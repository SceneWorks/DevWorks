# Shared operation architecture experiment

Candidate native Rust DTOs, generated JSON schemas, deterministic message fixtures and a SQLite receipt/control contract model. This is not the future `devworks-core` crate or a production SDK. Source/schema regeneration and tests are documented in [the evidence README](../../docs/architecture/validation/operation-contracts/README.md); semantics live in [shared operation contracts](../../docs/architecture/shared-operation-contracts.md).

`src/lib.rs` owns shared DTOs; domain modules extend them. `emit` regenerates the full schema manifest set. The fixture harness separately checks schema validity, typed semantic validity and normalized fingerprint rules. `probe_receipts.py` runs scripted transaction/race scenarios against actual SQLite. `build_register.py` keeps every retained catalog operation visible while domain schemas remain pending. No inference is executed.

Provider/session/package DTOs now live in `src/provider.rs` and `src/package.rs`, reusing generic common receipts. The owned helper in `src/package_probe.rs` is a disposable framing/RPC experiment. See [current combined evidence](../../docs/architecture/validation/provider-package-contracts/README.md) for protocol fixtures, native state models, process probes and source boundaries. No live provider or application effects are run.

Data/graph/retrieval/artifact/delivery DTOs live in `src/data_delivery.rs`. See [data/delivery evidence](../../docs/architecture/validation/data-delivery-contracts/README.md) for current combined checks, the [native store-port subset](../store-port-eval/README.md) and temporary Git probe. Historical reports preserve the source/schema digests of their original passes.


The complete catalog wire candidate now uses [domain-spec.json](domain-spec.json) as its explicit authoring source. `build_domain_contracts.py` generates and formats `src/domain_generated.rs`; `src/domain_support.rs` owns bounded scalars/collections/faults and `src/domain_rules.rs` the recorded pure cross-field checks. This large union is a schema qualification tool, not a proposed monolithic production dispatcher. Actual domain services/host authority/descriptor/SDK/provider behavior remain separate work.

**Schema revisions.** `build_register.py`, `verify_domain_contracts.py` and `audit_domain_sources.py` take `--date` (default: the run date) for the dates they record. `domain-spec.json` lists every operation that negotiates more than revision 1 under `schemaRevisions`, and a record gates a member introduced later with `since` (an optional field); a union gates a member of one variant with `variantSince` (`{"Variant": {"member": N}}`), which both generators honor (the variant's schema arm, the Rust `gated_member` deserializer and the `Revisioned` projection that drops the member below revision N). Hand-written specialized DTOs gate a member with `#[schemars(extend("x-since" = N))]`, the `gated_member` deserializer and a `Revisioned` implementation. `emit` writes the base revision-1 document of every schema plus `<name>.rN.schema.json` for each revision N that introduces members; request envelope documents carry the optional `schemaRevision` member. `build_register.py` binds each operation's per-revision documents (`schemaRevisions`), which `tools/core-codegen/generate.py` checks against the spec. A fixture entry `<name>.rN` is checked against revision N's document and strict reader, and a plain entry against revision 1's. The schema-revision pass wrote its verifier and source-audit reports to `docs/architecture/validation/schema-revisions/` instead of `domain-contracts/`, so that earlier reports keep the digests of their original passes. The history/session revision-2 pass wrote its reports to `docs/architecture/validation/history-session-revisions/` for the same reason. The resources revision-2 pass wrote its reports to `docs/architecture/validation/resource-revisions/`. The session-times revision-2 pass (`SessionRecord.createdAtMs`/`lastActivityMs` for the five session operations that return a session) wrote its reports to `docs/architecture/validation/session-revisions/`. The diagnostics revision-2 pass wrote its reports to `docs/architecture/validation/diagnostics-revisions/`. The router-availability revision-2 pass wrote its reports to `docs/architecture/validation/router-revisions/`. The provider-connection revision-2 pass (`router.connections`, `router.catalog`, `router.configure`) wrote its reports to `docs/architecture/validation/connection-revisions/`; it also fixed `build_domain_contracts.py`, which closed a union's generated `Revisioned` impl with one brace too many the first time a union carried a revisioned record. The Knowledge revision-2 pass (twenty-one `knowledge.*` operations and `dreaming.revert`) wrote its verifier and source-audit reports to `docs/architecture/validation/knowledge-revisions/`; it adds no source binding. The jobs revision-2 pass wrote its reports to `docs/architecture/validation/job-revisions/`. The work revision-2 pass (`WorkRecord.readiness`, `.pendingReadiness`, `.queueRevision`, `.workflowRevision` and `.acceptanceTests` for the twenty operations returning a work record, `FeaturePatch.readiness` and `.acceptanceEvidence` for `features.edit`, and the `placement` of `features.prioritize`, `issues.prioritize` and `tasks.prioritize`) wrote its reports to `docs/architecture/validation/work-revisions/`. The web-tools revision-2 pass (`web.search`, `web.fetch`) wrote its reports to `docs/architecture/validation/web-revisions/`. The indexing-status revision-2 pass (freshness, language coverage, semantic packs and overlays on `RepositoryIndexStatus`) wrote its reports to `docs/architecture/validation/indexing-revisions/`. A union alternative introduced later is annotated `x-since` like a member: earlier revision documents omit it, and the earlier revision's reader refuses it. An exactly-one member choice lists each alternative's full required set, so an earlier document folds back to its recorded `required` list. A definition annotated `x-earlier: {name, before}` takes, or merges into, its recorded name below `before`, so revision-1 documents stay byte-identical. A `name` that is a generic schemars family (`Page`, numbered `Page2`, `Page3`, ... by first use) merges into the family member the definition equals once the other renames apply. In domain-spec, these come from `exactlyOne`, `fieldSchema`, `schemaName` and `earlierName`.

The authoring Python must match the installed jsonschema/rpds wheel ABI. The retained ignored dependency directory currently has Python 3.12 wheels; a default Python 3.14 cannot load its rpds extension. Use the matching bundled authoring interpreter or install compatible packages in a separate authoring directory. No Python runtime becomes a product dependency. Current [evidence](../../docs/architecture/validation/domain-contracts/README.md) records the observed failure and successful matching-interpreter run.

`verify_domain_contracts.py` combines the 707 new messages with the prior 322 cases, cross-checks native decoding/semantic expectations and JSON Schema, verifies every selected input/result and both modes for hybrid names, discloses legitimate shared input aliases, and reruns the 12 native stream/history scenarios. Historical helper frames are replayed as data, not claimed as new process execution. `audit_domain_sources.py` checks the frozen inventory file bytes and complete schema/ownership bindings; it does not assert retained source method semantics or actual native parity. No inference or application effects run.

Knowledge revision 3 adds independent challenge records on every claim and full sourceLabel cleanup selectors alongside the legacy sourceId form. Earlier revision schemas stay byte-identical. The shared revision-3 result document also carries the existing artifact revision-3 outputs, so recorded fixtures cover both families.

Package revision 3 exposes saved schema-bound configuration and disabled-project overrides in package catalog and lifecycle replies. Revision 1/2 documents remain unchanged. The native Add-ons editor reads revision 3, retains unsaved text and its original compare-and-set revision across refreshes, and reloads saved overrides after restart. No operation or SQLite migration is added.


The DW-71 eval contract adds `evals.grade`/`evals.results`, immutable supplied suite snapshots and persisted report shapes through the same generators. Both built-in deterministic predicates are proxies. `EvalCoverage` preserves ungraded reason counts and uses only passed/failed instances in rates; `EvalRevisionContext` preserves partial sources in explicit Mixed attribution. Schema/model verification for this addition is recorded under `docs/architecture/validation/eval-contracts/`; those checks qualify shapes and pure arithmetic, while the native evaluator's separate acceptance verifies storage, history attribution and authority.
