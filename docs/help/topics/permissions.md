# Permissions, roles, and exact human authority

The app checks the authenticated actor, current role, scope, selected operation/mode/schema, enabled tools, grants, and current controls. Request bodies, page content, Help, user-created role text, and package output cannot mint authority. Instructions describe a task; they do not grant tools.

## Access profiles

Full access means selected tools run with your ordinary user rights subject to harness checks. Project scope limits brokered operations to the project and requires the appropriate bounded exception for native execution. These are enforcement guarantees, not claims that arbitrary native executables run in an OS sandbox. Code reviewers remain read-only even when another role is more permissive.

Protected Git branches, destructive confirmations, current project lifecycle, ownership, disabled tools, prerequisites, and required verification remain effective. Exact approval binds one reviewed request and source; it is not a reusable general token. An Agent stays attributed as Agent after human authorization. A package cannot impersonate a human by sending a field or invoking a generic command.

## Read access matters too

Artifacts, native continuation, project records, package guides, and generated references are served through current visibility. Knowing an artifact ID, cursor, or Help link does not grant access. Shared-repository membership does not expose every private project record.

If denied, inspect the actual role/scope/tool setting and the recorded reason. Do not weaken a policy to make a stale request pass. Review a permitted exact new request where appropriate. See [Approvals](help:approvals), [Settings](help:settings-Safety), and [SDK permissions](help:sdk-manifest).
