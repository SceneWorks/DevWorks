# Exact decisions and notification history

Approvals is directly below Chat in the left navigation. Inbox and History are global with project filtering; inspect an entry to read its exact target, revision, digest, reviewed source, rationale, and current staleness. Knowledge review is informational and requires a project selection; it does not create rule-approval authority.

## Make a decision

Read the complete reviewed plan, settings, operation preview, or risk finding. Large source content may be paged from an immutable artifact. If it cannot be read or its identity changes, refresh before deciding. Only the app's dedicated human interaction can record a human decision. A tool cannot become human by supplying a flag, an actor ID, or a token.

An approved saved operation returns through current admission and authorization as its original actor. Changed arguments, stale source, disabled tools, narrowed permissions, archived projects, and independent holds still matter. Approval does not clear a user pause or bypass a protected Git action. An uncertain result is reconciled using the same saved operation identity; do not issue a different command just to get a response.

## Notifications are separate

Opening or reading a notification can mark it read. Explicit acknowledgment dismisses a completion card and retains it in history. Neither action approves a proposal, resolves a readiness finding, nor resumes execution. Completion cards represent verified feature/issue completion, newest first, and remain until explicitly dismissed.

Required-input desktop alerts depend on app focus, platform permission, valid app identity, and notification settings. Denied, suppressed, unavailable, failed, or uncertain OS delivery retains the persistent in-app notification. System acceptance does not prove that an alert was visible.

See [Settings and proposals](help:settings), [Readiness](help:features), and [Recovery](help:recovery).
