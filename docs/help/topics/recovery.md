# Conflicts, uncertain outcomes, and safe recovery

A revision conflict and a lost acknowledgment need different responses. A conflict says the view you edited is no longer current. An uncertain outcome says the original action may already have committed or dispatched.

## Conflict

Keep the exact draft, refresh the authoritative record, compare the changes, and explicitly rebase or revise the draft. Use the new current revision only after that review. Do not overwrite a concurrent connection, plan, settings, or work edit by silently substituting a newer revision.

## Uncertain command or effect

Preserve the original command/request key and normalized arguments. Use Confirm or the returned receipt/operation recovery action. Replay of the same request can return its original receipt without repeating the effect. Changing arguments under the same key is refused; issuing a fresh key before reconciliation can create duplicate work.

An interrupted provider stream can have durable partial text/usage and an unknown remote tail. An interrupted Git/package/browser/process action can need an observed outcome before ownership changes. A local process stopping or a transport closing is not proof that every remote effect stopped.

## Restart

The engine recovers durable records before new admission. Pauses, unresolved effects, restore epochs, lease generations, assignment generations, and project lifecycle remain meaningful. Do not delete store rows or managed directories to make a wait disappear. Continue, resource release, approval, and acknowledgment each clear only their own permitted condition.

Missing Help/package guides are not repaired by substituting another version. Read the availability reason, refresh current metadata, and use the exact installed version. See [Controls](help:work-controls), [Approvals](help:approvals), [Storage](help:storage-lifecycle), and [Diagnostics](help:diagnostics).
