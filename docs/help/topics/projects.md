# Projects, archives, and deletion

All projects lists Active, Archived, and Deleted projects. Select a project to work in its Overview, Features, Issues, and Repositories. Project selection changes the scope of those screens; it does not move work or grant access to another project.

## Create and connect

Create a project with a clear name and default workflow. Register repositories that belong to it. One registered repository can serve more than one project; project membership is distinct from physical files. Reusing a repository does not merge the projects' work, histories, permissions, or budgets. See [Repositories](help:repositories).

## Archive safely

Archiving keeps project records and history. If work is active, review the app's warning and explicitly confirm. Confirmation stops that project's work and blocks new dispatch, including its project jobs and keep-working selection. Other projects continue. A later restore leaves execution stopped; restoring records alone does not resume agents, schedules, or keep-working mode. Review current state and explicitly restart what you intend.

Permanent deletion is separate from archival and requires its own review. It removes managed harness data and eligible artifacts, while preserving shared data still referenced elsewhere. It must leave local repositories, branches, worktrees, and GitHub resources untouched. A delete action is not repository cleanup. If the app refuses because work or effects remain unsettled, inspect the outstanding operations rather than deleting files behind the app.

Project actions use current revisions. A conflict means someone changed the project after your view loaded: refresh and review before retrying. A lost acknowledgment is different; confirm the original operation first. See [Recovery](help:recovery) and [Storage and lifecycle](help:storage-lifecycle).
