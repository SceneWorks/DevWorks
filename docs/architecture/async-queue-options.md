# DevWorks asynchronous queue dependency review

1 November 2026 · Architecture decision support · No application implementation

Adopt Tokio's existing bounded channels for live dispatch and notifications. Keep authoritative work/event admission inside the application's SQLite transaction through the existing persistence ports. This reuses the runtime and storage engine; it does not introduce a custom channel implementation, AMQP server or general-purpose broker. Application eligibility, approval, pause and uncertain-effect rules remain application logic with any library.

## Options and fit

| Option | Evidence and fit | Decision |
| --- | --- | --- |
| Tokio | Bounded `mpsc` supports async dispatch and synchronous worker bridging. `oneshot` returns one result, `watch` carries latest state, and `broadcast` supports ephemeral fan-out with explicit lag errors. All are live-process channels. | Selected for live communication. A supervised dispatcher feeds bounded workers; no receiver-cloning workaround or handwritten channel. |
| Crossbeam channel | Synchronous bounded/unbounded MPMC with blocking operations. Useful for a demonstrated dedicated synchronous worker-pool need; it supplies no on-disk recovery. | Do not add a second channel stack without a concrete need or measurement. Never block an async runtime/UI thread on its receive. |
| Flume | Bounded MPMC with synchronous and async APIs. It could simplify a mixed worker pool; it supplies no durable domain transaction. | Viable alternative if mixed-worker evidence warrants it. No default dependency alongside Tokio channels. |
| `msg-broker-rust` | An embedded library API exists. Inspected code stores messages in separate per-topic files, keeps consumer-group offsets in in-memory maps, and returns an unbounded embedded subscription channel. The append path flushes its buffer but the inspected path has no file sync call. | Not selected for authoritative work. A separate log introduces state/log dual-write recovery, and the inspected offset/buffer behavior does not meet the adopted queue contract without additional work. These are source observations, not a complete project audit. |
| RobustMQ | The provided article describes broker, metadata and journal components; the inspected current workspace also includes broker/storage/meta/admin modules. Its protocol/distributed-broker surface is substantially broader than local application dispatch. | Not selected as a desktop queue dependency. No claim that Rust source could never be embedded; there is no demonstrated benefit here that offsets the integration/storage footprint. |
| Apalis plus SQLite | A closer durable-job candidate: workers, delayed jobs and retry infrastructure over SQLite. Inspected `apalis-sqlite` 1.0.0 setup selects `synchronous = OFF`; its storage uses its own SQLx persistence/worker semantics. | Do not adopt unchanged. Evaluate reusable worker/backend components only if they preserve the same-transaction outbox, chosen write ownership, durability, manual Continue and uncertain-effect fencing without creating parallel state machines. |

## Contract to preserve

A task transition must commit its history event and required follow-up work atomically. Publishing to an independent broker after committing domain state leaves a crash gap; publishing first can expose work for a state change that rolls back. A standalone persistent broker does not by itself eliminate that application outbox requirement. SQLite already owns the authoritative records, and its transaction can include the pending delivery. [SQLite transaction guarantees](https://www.sqlite.org/transactional.html)

Use bounded Tokio `mpsc` for the storage-owner mailbox and admitted work dispatch. Send only owned DTOs/identifiers across it; the UI uses nonblocking admission and receives a Busy/waiting state rather than blocking rendering. A dispatcher claims only as much durable work as its worker capacity can accept. The channel buffer is not another durable queue. The capacity limits buffered work/resources, not the number of logical agents globally.

Use `watch` for coalesced latest-state wakeups, `oneshot` for one response, and bounded `broadcast` for optional transient UI notifications. A broadcast lag error triggers a durable cursor query; it must never lose a required handler's work. After commit, send a best-effort wakeup. Startup and a bounded periodic sweep find eligible rows if a wakeup was lost. No token-by-token SQLite commits or unbounded-memory backlog is implied.

`events` carries immutable identities, aggregate revisions, causation/operation references and versioned payloads. `queue_entries` identifies a delivery by consumer plus event, with durable priority, ready time, attempts, owner/lease, cancellation epoch and fencing generation. `consumer_progress` advances only through a contiguous applied prefix; individual completed-delivery receipts handle out-of-order completion. Static required consumers are enqueued in the original state transaction. Versioned package subscriptions use the existing durable cursor protocol, never ephemeral broadcast as their source of truth.

Each handler's database effects, delivery completion and follow-up intents commit together. External I/O runs outside that transaction, under a stable operation ID and the shared effect journal. A crash after an external commit but before acknowledgement triggers observation/reconciliation, not unconditional replay. Enforce at-least-once delivery and idempotent application; do not promise exactly-once external actions.

Ordering is per aggregate or explicitly declared partition when required. Independent repositories, work roots and consumers may run concurrently. A failed required stage prevents only its dependent stages from becoming eligible. Retry transient failures with durable bounded backoff; deterministic malformed/unsupported payloads and exhausted retries enter a visible Failed/NeedsInput delivery state. Do not spin, silently discard poison events or advance past a gap as though a handler succeeded. A retry command revalidates schema, work control, authority and effect safety. Resolving an event is not Continue authority.

On close, stop admission and reconcile/checkpoint claimed work; do not drain an arbitrarily long backlog before exit. On reopen, reconcile stale claims under the new boot identity. Feature/issue effects remain held for explicit Continue; eligible maintenance/schedules follow their distinct recovery class and restore holds. Lease expiry alone cannot transfer a still-running process or authorize a retry of an uncertain mutation.

Expose pending/claimed/waiting/failed counts, oldest eligible age, attempts, causes, consumer cursor lag and operation links in diagnostics. Compact acknowledged delivery bookkeeping only after the required consumers and references permit it; preserve domain history, unresolved operations and artifact retention. Backlog/disk quotas stop or defer new optional work visibly and reserve headroom for control/history/ack writes. Do not delete accepted work to make a queue appear healthy.

## Qualification before dependency freeze

Exercise the real native adapter/runtime without inference: commit/rollback admission, lost wakeups, bounded dispatch saturation, broadcast lag recovery, duplicate deliveries, fan-out consumer failure, required partition ordering, old-owner fencing, deterministic poison events, shutdown/reopen/restore classes and a lost response after an external fixture effect commits. Measure queue lag and control-write latency while indexing and streaming scripted provider events. If a job library reduces this implementation while passing the same contracts, adopt it through the ports; do not add a generic broker framework merely to wrap standard channels.

Source review used Tokio 1.54.1 documentation, Crossbeam channel 0.5.17 and Flume 0.12.0 documentation, and fetched repository files whose blob hashes are retained in queue-review evidence. These are review observations, not selected release dependency pins or benchmark results. No broker or job framework was built, installed as an app dependency or runtime-tested in this review.
