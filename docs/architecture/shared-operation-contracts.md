# Shared command, query and event contracts

Current baseline 1.1 adds [incoming MCP server contracts](mcp-server-contracts.html) and four typed internal administration operations. The current register has 353 operations in 48 families; historical counts below describe their original checkpoints. New MCP transport/authentication/client behavior remains DW-063/064 implementation acceptance.

Adopted architecture candidate `1.0-draft.1`, 1 November 2026. AD 48–51. Confidence: high in the semantics; production gateway, adapters and target qualification remain pending. This is an in-process application boundary with versioned package/tool representations, not a new HTTP server or a public SDK v1 freeze.

Success for this pass is explicit authority ownership, unambiguous receipt/retry semantics, bounded scoped reads/events and concrete root-control messages checked through native Rust DTOs and generated schemas. The subsequent complete domain pass supplies the other retained input/result candidates. This common contract alone does not freeze public SDK interoperability.

## Ownership and the trust boundary

`ApplicationGateway` accepts a typed command/query plus a host-created `InvocationContext`. UI adapters, tool/MCP adapters, schedules and package host calls use that same boundary. The context contains the resolved principal and invocation/session identity, ingress namespace, store/restore epoch, project/work/assignment lineage, current capability registration, policy/control/ownership revisions and host authority-source references. Those fields are not deserialized from a tool argument or model message. Scope requested in an argument is a target to validate, not a grant.

A user action can mint a specific host authorization receipt. An agent can exercise that receipt only within its recorded binding. Text claiming to be a user, an actor ID in JSON, a package declaring Full access, a schedule, or a copied receipt ID cannot mint authority. Resolve approval/Continue grants through current host records, ownership and revocation checks. An agent invocation stays attributed to that agent with the human authorization source separately linked; it does not become the human actor.

Keep three IDs distinct. `requestKey` identifies one caller intent for retries within a host-resolved namespace; it is not authority. The gateway assigns a durable `CommandId` to the recorded decision. An `OperationId` identifies asynchronous/effectful work and appears only where that work exists. Repeated attempts belong to the same operation with separate `AttemptId`s. A UI notification ID, tool call ID, command receipt, queue delivery and external effect are not interchangeable identities.

The [candidate Rust DTOs](../../tools/contracts-eval/src/lib.rs) generate the [schema set](contracts/manifest.json). [Schemars](https://docs.rs/schemars/1.2.3/schemars/) is the probe's schema generator; [Serde unknown-field rejection](https://serde.rs/container-attrs.html) prevents silently accepting fields outside the selected message contract. There is no public `execute_sql`, arbitrary trusted context constructor or generic caller-selected policy bypass.

## Message and scalar rules

Use [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core) for external message descriptions and strongly typed Rust records internally. The candidate protocol string is exact, `1.0-draft.1`. Strict tagged variants reject unknown command names, unknown fields and unsupported versions. No reader may interpret an unknown mutation as a known one by discarding fields. Future additive capabilities must negotiate a supported schema revision before use. Stored schema revisions need explicit upcasters or a visible incompatible-record hold; do not rewrite historical requests in place.

IDs and request keys are opaque bounded ASCII identifiers, 1–128 characters. They never imply authority, sort order, a filesystem path or a semantic parent. Revisions, generations, durable sequences, epochs and UTC millisecond timestamps serialize as canonical decimal strings, preserving exact signed-64-bit values across SDK languages. Revisions/sequences that identify a committed event are positive; initial watermarks/epochs may be zero. Schema checks lexical form; typed decoding additionally rejects values above `9223372036854775807`. No leading zero, exponent, sign, whitespace or floating-point spelling is accepted. Increment is checked, never wrapped.

Normalize validated typed messages before fingerprinting: omitted and explicit-null optional fields have the same typed absence; covered hold references sort by ID; duplicate hold IDs are invalid even if their revisions differ. Do not normalize user text, Unicode content or array order unless that particular field is explicitly a set. Compute SHA-256 over a versioned normalized command representation using [RFC 8785 JCS](https://datatracker.ietf.org/doc/html/rfc8785). Preserve the exact contract revision and digest with the receipt. A changed expected revision is a changed intent. Conflicts name both the subject and revision dimension (work, control, blocker, operation, policy, scope, plan or authority), so two counters on the same root cannot be confused. JSON whitespace/object-property order is not. Request keys, transport retry counters and deadlines do not change the command fingerprint. These are hashing semantics, not permission grants. The probe uses an established authoring JCS library; the native JCS implementation still requires conformance qualification.

**Native fingerprint representation (DW-1, 2 November 2026).** `devworks-core` fingerprints the lowercase hex SHA-256 of the RFC 8785 JCS form of `{contract, operation, mode, schemaRevision, input}`, where `input` is the strictly decoded, normalized, re-serialized selected input. The envelope `protocol` member and the caller identity (`requestKey` for a Command, `queryId` for a Query) are excluded; the contract revision enters through `contract`. **Decision · confidence medium-high:** a `timeoutMs` input field is an execution parameter, not a pure deadline: it bounds how long the effect (query, command, request or container run) may execute and therefore what the operation may do, so it stays in the fingerprint and a changed `timeoutMs` under the same key is an `IdempotencyConflict`. A caller's wait deadline for the reply is not an input field and never enters the fingerprint.

**Negotiated schema revisions (3 November 2026).** Every operation registers the schema revisions it accepts; the [register](contracts/family-coverage.json) lists them per operation (`schemaRevisions`), each binding its own input, result, reply and completion documents. A request negotiates one with the optional envelope member `schemaRevision`, a JSON integer 1–65535 on every operation request envelope (domain and specialized alike); absence means revision 1. Admission resolves it right after selecting the operation and mode and before authority: a revision the operation does not register is `UnsupportedSchema` (retry `Never`) for a Command and a `SchemaMismatch` fault for a Query, and a malformed member is an invalid request: a non-integer, a value outside 1–65535, or a non-integer spelling of an integer such as `1.0` or `2e0`. JSON Schema 2020-12 matches `1.0` as an integer, so the documents cannot refuse that spelling; the typed reader refuses it, as it does for every other integer member. A well-formed revision that is not registered is never treated as malformed. Neither reaches the store, mints a receipt or writes history. **Decision · confidence medium-high:** negotiation is per request, not a host capability handshake. The rules above require negotiating "a supported schema revision before use", and the [domain contracts](domain-operation-contracts.html) make "the registered schema revision" decide the exact projection. Gateway calls arrive from UI actions, tools, schedules, package host calls and MCP without a shared session, and an in-process caller has no handshake. A per-request revision becomes part of the recorded intent, so retries and replays carry it. Adapters that do negotiate (package `host.initialize`, MCP initialization) map their negotiated version onto this member; they never widen it. **Decision · confidence medium:** the member is an integer rather than a canonical decimal string. It is a small contract version, not a signed-64 store counter, and the fingerprint document already carries it as a JSON number, so revision-1 fingerprints are unchanged.

Revisions are additive. A member introduced at revision N is optional and annotated `x-since: N`. The base `<name>.schema.json` document is revision 1, and `<name>.rN.schema.json` is the shape at revision N and later (it requires `schemaRevision` of at least N). An earlier document omits every member introduced later, together with the definitions only those members use. Each revision has its own strict reader. A member introduced after the negotiated revision is refused as an invalid request, never discarded. A revision-gated member has no explicit-null spelling: it is omitted or carries a value, so an earlier reader always sees it. A change that is not additive needs a new input/result type plus an explicit upcaster for stored records; none exists yet.

The fingerprint binds the negotiated revision (the `schemaRevision` member above). An absent member and an explicit 1 are the same intent. Revision-1 normalization and the fingerprint document are unchanged, so existing revision-1 receipts keep their digests and replay as before. The same request key under another registered revision is `IdempotencyConflict`, even when the remaining input is equal: the caller asked for another contract, which is a different intent. The receipt stores its revision, and a replay returns it under that revision's projection. A receipt whose revision the operation no longer registers is an incompatible-record hold (`ResolveReceipt`, one `ReceiptIncompatible` history entry), never replayed. The gateway publishes every query result and records every receipt decision under the negotiated revision's projection. A revision-1 caller therefore receives exactly the revision-1 shape that a strict revision-1 reader decodes. This is not an older, weaker projection that hides an outcome: it omits only members the caller's contract never had, every outcome and authority requirement is unchanged, and a receipt recorded under a later revision cannot be replayed through an earlier one.

Bound ingress bytes before parsing: initial common envelope maximum 1 MiB, with tighter capability-specific limits; use artifact references/streaming for larger content. Reject duplicate JSON member names, non-finite numbers, invalid encoding, excessive nesting and incomplete frames before dispatch. The native probe checks the byte bound and typed duplicate fields; complete parser depth/host framing qualification remains pending. Event pages are 1–500 items; blocker summaries contain at most 100 items with `hasMore`. A truncated blocker list cannot make `eligible=true`. Opaque cursors are at most 4096 bytes and validated by the owning query port. Application-wide limits are engineering defaults, not a global agent-count cap.

## Command admission and receipts

1. Validate framing/schema and bind the host invocation. Resolve current visibility/authority to address the target without exposing another principal's receipts.
2. Form receipt identity `(actorId, scopeKey, requestKey)`. `scopeKey` is a host encoding of store identity, restore epoch and ingress namespace. The target root and all command fields are in the fingerprint. A caller cannot choose `scopeKey`; different sessions do not automatically share a tool invocation namespace. UI retransmission retains its namespace/key, and durable tool-call retries retain their original invocation namespace/key.
3. On the sole write owner, check an existing receipt before current expected-revision/CAS evaluation. Equal fingerprint returns that receipt; a different fingerprint returns `IdempotencyConflict` with no new effects. Revalidate access before publishing the old receipt. A revoked caller receives a denial rather than old sensitive content; no receipt replay redispatches work.
4. For a new command, check current effective authority/grants, expected revisions, root controls, eligibility and target identity. Terminal semantic decisions such as `ContinueRequired`, `Blocked`, `RevisionConflict` and `Archived` are durable receipts. Pure malformed/unsupported/permission denials before admission do not mint durable work or allocate an unbounded receipt record. If transient storage admission fails before any write, return an explicit rejection with same-command retry advice.
5. In one transaction, commit the decision receipt, `CommandDecided` history, actual domain changes, consumed grant usage and outbox intents. Successful control mutation and its durable activation/wakeup cannot split. Receipt-only decisions do not mutate work. No network/process/model callback runs in this transaction.
6. Return `Recorded` only after a confirmed commit. Its receipt reports the decision at `committedSequence`, not present execution status. `replayed=true` labels a historical response. Fetch current state independently. `Accepted` does not prove a child launched, a process stopped, a merge happened or a feature completed.

The initial SQL fixture already has `command_receipts`, `events`, `operations` and `queue_entries`. Store the candidate receipt/contract revision in validated JSON and retain the existing relational uniqueness; `scope_key` now has an explicit host meaning. An `OperationId` is nullable for decisions with no new operation. The schema fixture is not a production migration.

If the commit acknowledgment is lost, return `CommandStatusUnknown`; use receipt lookup or resubmit the exact same command/key. Never invent a new key merely because a response timed out. `CommandStatusUnknown` concerns local admission; `OutcomeUnknown` concerns an external operation that might have taken effect. The latter requires its reconciler, even after a receipt is found. Cancellation of a caller does not establish transaction rollback or external cancellation. A new command after a recorded conflict/blocked decision requires refreshed state and a fresh key; the old key remains its original decision.

Use typed retry advice: `Never`, `SameCommand`, `AfterBlockerClears`, `ResolveReceipt`, `ReconcileOperation`, `RefreshAndNewRequest`. The owning use case supplies it from known state, rather than inferring safety from a timeout or an HTTP status. A request deadline controls waiting/admission; it cannot revoke a committed effect by itself.

Retain command identity/digests while related work/effects/history remain retained. Do not expire correctness records as disposable logs. Explicit history deletion or logical export must preserve the retained deduplication boundaries or start a fresh namespace; it must not silently make an old request executable again. Backup restore changes the epoch, keeps restored automation stopped and reconciles external effects; old epoch receipts remain historical and cannot serve as fresh execution/approval authority.

## Concrete root controls

| Command | Untrusted body | Transaction and response |
| --- | --- | --- |
| `runs.start` | Root ID, expected work revision, expected control revision | Validate a feature/issue root. Paused/manual-resume-held roots return `ContinueRequired`. Existing enabled activation returns `AlreadyActive`. Explicit feature planning may proceed without implementation approval, but only approved implementation may dispatch. An actionable issue follows its confirmed policy. Commit one activation intent or the truthful blocker decision. |
| `runs.pause` | Root ID and expected control revision | Each distinct authorized Pause creates/renews its human-pause latch, advances the control/cancellation generation and records stop intent. This includes a renewed Pause while already stopped, so an earlier pending Continue cannot clear a later user action. The same key is a replay and does not renew it twice. Receipt acceptance precedes asynchronous quiescence; retain uncertain effects/resources until verified. |
| `runs.continue` | Root ID, expected control revision, 1–128 exact hold ID/revision references | Resolve a host-issued authorization source bound to this command/root/covered holds. Validate every covered current latch before clearing any; reject stale/new/unknown holds atomically. Clear only authorized manual-resume latches, preserving independent approval/dependency/reconciliation and other blockers. Commit enabled control/wakeup and return `Accepted` even if a separate blocker still prevents execution. Descendants are reevaluated individually under the existing root limit. |

Maintain one current root latch per manual-resume cause, renewing its revision rather than accumulating duplicate active Pause/restart/budget latches; prior changes remain history. This bounds the covered current control conditions without discarding operation/assignment-specific blockers.

Only root feature/issue IDs are valid manual control targets. An assignment ID is `InvalidTarget`, not an instruction to implicitly resume its parent. `runs.eligibility` may inspect a child; internal child wakeups/dispatch recheck ancestor controls and its own blockers. No child Pause/Continue command or manual child latch is introduced.

A Continue authorized for pause revision N cannot clear N+1, a new restart hold or a later budget latch. Approval of an operation does not mint Continue authority. A cost-limit increase does not clear the budget/manual-Continue latch. Direct current user Continue can cover the specific restart/budget holds; an ordinary automation delegation cannot waive those manual conditions. No eligible descendant is restarted twice when duplicate UI/tool requests or wakeups arrive.

Pause linearizes admission at the write boundary: later admissions cannot use old control revisions. Previously admitted effects may still finish, stop cooperatively or become uncertain. Report those states separately; logical cancellation, process termination and outcome reconciliation are different facts. Resource handoff requires actual prior-owner quiescence in addition to fencing.

**History and session revision 2 (3 November 2026).** `history.events`, `.work_lineage`, `.git_links`, `.evidence_links`, `.tool_usage` and `sessions.briefing` register revisions 1 and 2. Revision-1 callers are unchanged: the same inputs, results, cursors and page rule.

Every revision-1 schema document is byte-identical to the one recorded before these revisions, with two exceptions; a test checks the recorded digests.
- The documents that carry every operation (`domain-request`, `operation-result` and the domain reply and completion documents) gain the branches of the new `artifacts.tag` operation.
- `RelativePath` is hardened at every revision, as a fix rather than a revision change (see the briefing inputs below). For this pattern the documents are not validation-equivalent: a revision-1 path that was platform-absolute or escaping is now refused.

How the revision documents are produced:
- A union alternative introduced at N is annotated `x-since: N`, like a member. An earlier revision's document omits it, and that revision's reader refuses a value carrying it, because an alternative cannot be cleared from a value. The gateway also refuses to publish such a value (an event's command aggregate below revision 2) as a handler fault.
- An exactly-one member choice lists each alternative's full required set. An earlier document that is left with one alternative folds it back into the recorded `required` list, and a union left with one bare alternative becomes that alternative.
- A definition annotated `x-earlier: {name, before}` is the recorded definition `name` below `before`, with its later description dropped. It takes that name, or merges into it and must equal it exactly. Definitions named after it, such as `List_<name>_0_500`, follow. `EventSubject`, `EventRevisionKind` and `AttributedGitLink` therefore read as `Subject`, `RevisionKind` and `GitLink` at revision 1.
- `UsagePage` keeps the recorded `Page` schema name.

Revision 2 adds:

- **Tail checkpoint.** History pages (`HistoryPage<T>`, the recorded `Page` shape under the same schema name, and `UsagePage`) carry `checkpoint`: the continuation after the last fact the page covers. It is present on every page, including the current tail; an empty page keeps the position it was asked from. While `hasMore`, it equals `nextCursor`. **Decision · confidence medium-high:** a separate member rather than `nextCursor` at the tail. The recorded revision-1 rule ties `nextCursor` to `hasMore`, and a revision-1 reader must keep that rule, so the checkpoint cannot reuse the member. Cursors issued at revision 2 also bind the negotiated revision, because a revision-2 page covers facts a revision-1 page does not.
- **Command aggregate.** `Event.aggregate` is `EventSubject`: the recorded `Subject` variants plus `command` (the decided command). `Event.aggregateRevisionKind` is `EventRevisionKind`: the recorded kinds plus `Command`. A command aggregate is the event's own `commandId` at revision 1. **Decision · confidence medium-high:** these are new unions used only by `Event`, rather than new variants of `Subject` and `RevisionKind`. Blockers and revision conflicts use those two, and they can never name a command. Widening them would put the alternative into every root-control result and reply document at revision 2. A root's revision-2 feed has every decision attached to the root, including decisions attached only through the invoking agent's lineage.
- **Project change feed.** `history.events` takes exactly one of `rootId` and `projectId`; revision 1 requires `rootId`. The project feed has every command decided in the project, in committed-sequence order: every write passes the gateway as one. A decision belongs to a project in this order:
  1. its work target's project;
  2. else the invoking lineage root's project;
  3. else the first project the command names (a `projectId`, or a project data scope) that the invocation may see, so a workspace command naming a project is in that project's feed;
  4. else the invocation's project.

  The feed is `NotFound` outside the invocation's authorized project scope. Its cursors bind the project, its scope revision and the principal. Store migration 9 indexes the project's decisions (a partial index on `events(project_id, seq)` for `CommandDecided`), so a page and its one-row has-more probe only seek matching rows. **Decision · confidence medium:** a scope alternative of the existing operation rather than a new one, because no catalog operation names a project feed. Work items, sessions and settings writes all reach it as decided commands. Workspace-level decisions without a project are not in any project feed.
- **Structured attribution (HISTORY-02).** `LineageRecord` and `EvidenceLink` carry `actorId`, `occurredAtMs`, `repositoryId` and `revision` (the repository revision a fact names). `AttributedGitLink` is the `GitLink` shape of `history.git_links` plus `actorId` and `occurredAtMs`; its repository and head are already fields. It is a separate record because `GitLink` is also embedded in work attempts, issues and pull-request results. Every value comes from the stored record. A related work item records no creator, so its actor is absent; its time is its creation. No work-item writer exists yet to record a creator.
- **Tool invocations.** Every completed invocation (a durable call and its single initial response) of every session is recorded, whether or not the session has a project or work root. Store migration 9 adds `tool_invocations`, indexed per root and per project and backfilled from the responses recorded earlier. Its writer floor is 9, because an older writer would append responses without their invocation facts. At revision 2, `history.tool_usage` names exactly one scope:
  - `rootId`, the only scope at revision 1;
  - `projectId`, visible to the invocation like the project feed;
  - `workspace: true`: the workspace's own Home sessions, read only by a workspace invocation of a principal whose authorized scope is the workspace (otherwise `PermissionDenied`, `workspace_scope`).

  Cursors bind the scope and the principal. An admin-wide audit reads the workspace scope and each project. `UsagePage.toolInvocations` interleaves with the inference usage in `items`, in committed-sequence order, and each list carries its committed sequences (`ToolInvocation.sequence`, and `itemSequences` in the order of `items`), so the commit order can be rebuilt. A page is read in one statement per source. There is one invocation per durable initial tool response, with:
  - the tool (capability) name and its outcome;
  - the call and session, and the operation a wait or unknown outcome is linked to;
  - the response's actor and time;
  - `durationMs`, the interval between the durable call and response records (0 when one batch carries both; execution timing is not recorded);
  - for a failure, its error code after redaction.

  Tool arguments and results never leave their restricted artifacts. A call without a response is not yet an invocation.
- **Briefing inputs.** `sessions.briefing` takes three new inputs:
  - `item`: a visible work item of the session's project, added as a `focus:` source.
  - `paths`: 1–128 distinct relative paths (`PathSet`, with `uniqueItems` in its schema). They scope path knowledge. No briefing source is path-scoped yet, and no path-scoped knowledge is stored, so they select nothing more today.
  - `budgetTokens` (1–1,000,000): the briefing is the longest prefix of its order whose summed `tokenEstimate`s fit. The estimate is 4 bytes per token, rounded up, over the material a source names. Left-out recorded sources continue through `sessions.context_sources`. No inference is involved.

  `RelativePath` treats both `/` and `\` as segment separators. It refuses:
  - a leading separator (`/x`, `\x`, `\\server`);
  - a drive form (`C:`, `C:x`, `C:\x`);
  - an empty, `.` or `..` segment under either separator (`..\`);
  - NUL.

**Artifact revision 3 and `artifacts.tag` (3 November 2026).** `artifacts.save` and `artifacts.list` register revisions 1–3. Revisions 1 and 2 are unchanged and still require `projectId`.

- **Workspace scope.** At revision 3, a save or listing names exactly one owner scope: `projectId`, or `workspace: true`. A workspace save is owned by the principal that saved it, with no project and no origin work. Only a workspace invocation (no project, no work lineage) of a principal whose current authorized scope is the workspace may save or list there; anyone else is `PermissionDenied`. The workspace's storage limit applies. Only those principals — the user, the host and unconfined principals — may save or list there. The workspace listing follows the existing artifact audience rules (`Viewer`): the user, the host and the unconfined workspace coordinator list every workspace artifact, and any other principal lists only the artifacts it owns. Its cursors bind the listing principal. Receipt replies are never listed. A project-bound handle never resolves for a workspace save.
- **`artifacts.tag`.** A new domain operation replaces the tag set of an existing artifact. It reuses the tag bounds and set normalization: at most 32 distinct labels of 1–64 characters, sorted, and an empty set clears the tags. The caller must see the artifact and act for its owner scope:
  - for a project artifact, a principal authorized for the owner project, invoked from that project or from the workspace;
  - for a workspace artifact, a member of its audience (its owner, the user, the host, the unconfined coordinator) whose authorized scope is the workspace.

  Seeing an artifact through a share never grants this. A confined or unconfined principal acting from a project the artifact is only shared with is `PermissionDenied`. The expected artifact revision guards concurrent edits. A changed set advances that revision and records `ArtifactTagsChanged`; an equal set is `NoChange`. The result is a `MutationSummary`. **Decision · confidence medium-high:** a new operation rather than a member of an existing one, because no recorded operation's selected variant changes an existing artifact's metadata, and selectors are single-valued. Like every operation, it starts at revision 1, and no earlier caller exists. **Decision · confidence medium-high:** a receipt's reply is never retagged (`Conflict`, `artifact_receipt_retained`). It is an immutable, system-owned correctness record that no listing returns, so tags could neither find it nor describe the user's own outputs.

**Resources revision 2 (3 November 2026).** `resources.list`, `.acquire`, `.renew`, `.release`, `.holders` and `.waiters` register revisions 1 and 2. Revision-1 inputs and results are unchanged; each revision-2 result projected onto revision 1 is the revision-1 result. Revision 2 adds:

- **Acquire.** `purpose` (at most 500 characters), `priority` (`Low`, `Medium` default, `High`, `Critical`), and `capacity` and `labels`, which apply when the acquire creates a project resource and must equal an existing resource's (`Conflict`), as CodeGraph holds do. Owner, session, project, work and assignment come from the host context, never from the request.
- **Records.** `LeaseRecord` carries `units`, `purpose`, `priority`, `queuePosition` (waiters), requested, granted, renewed and ended times, `endReason` (`Released`, `Expired`, `Cancelled`, `Reconciled`), `ownerUnreachableSinceMs` and the owning project, root, assignment and session. `ResourceRecord` carries `scope` (`Machine`, `Project`), the owning project, `physical`, `labels`, `used` and `available`.

**Decision · confidence medium-high:** a resource is addressed by name. A host-registered machine resource (for example the desktop, capacity one, physical) is one canonical `machine:<name>` resource for every project; any other name is the invoking project's `project:<project>:<name>` resource, created by its first acquire. The definition revision `expectedRevision` checks is the resource's definition (capacity, labels, physical), not its occupancy, so racing acquirers queue rather than conflict. **Decision · confidence medium-high:** a full resource queues the acquire as a `Waiting` lease the caller polls, instead of CodeGraph's blocking `wait_seconds`, because a command decides inside one short unit of work. Waiters are granted by priority, first come first served within one, strictly in order. A waiter keeps its place for 120 seconds after each poll. **Decision · confidence high:** an expired physical lease becomes `Uncertain` and keeps its capacity until every owned process serving it is reaped and no dispatch admitted under it is still running; only then is it `Reconciled` and the next waiter granted. A logical lease simply expires. Stale fences are refused at renew, release and dispatch.

**Session times revision 2 (3 November 2026).** `sessions.list`, `.get`, `.append_message`, `.start` and `.end` register revisions 1 and 2. Inputs are unchanged at both revisions; each revision-2 result projected onto revision 1 is the revision-1 result. At revision 2, `SessionRecord` carries `createdAtMs` (when the session started) and `lastActivityMs` (the latest of its start, its newest transcript entry and its end), store-clock UTC milliseconds. Chat History groups conversations by them (UI-03).

**Decision · confidence medium-high:** the times are read from records the store already keeps (the session row's start and end, the newest transcript entry's commit time), so the revision needs no migration and changes no stored data. **Decision · confidence medium-high:** every operation that returns a `SessionRecord` registers revision 2, not only `sessions.list`, so a client that asked for revision 2 sees the same record shape wherever a session comes back.

**Diagnostics revision 2 (3 November 2026).** `workspace.diagnostics`, `workspace.logs` and `workspace.record_diagnostic` register revisions 1 and 2. Revision-1 inputs and results are unchanged: their results are the new `DiagnosticPage` and `DiagnosticEntry`, which below revision 2 are the recorded `Page<Diagnostic>` and `Diagnostic`. `Diagnostic` itself, which indexing, knowledge, database and add-on operations also carry, is unchanged, so no other operation gains a revision. Revision 2 adds:

- **Records.** `DiagnosticEntry` carries its log `sequence`, `recordedAtMs`, the attributed `actorId`, `origin` (`Host`, `Reported`) and project, the run's `operation`, `operationId`, target, `stage`, `sourceRevision`, `attempt`, start and finish times and progress, its `outcome` (`Running`, `Succeeded`, `Partial`, `Stale`, `Cancelled`, `Retryable`, `Failed`) and `errorClass`, a health check's `health` (`Healthy`, `Degraded`, `Failed`, `Unavailable`), bounded helper `output` with `outputOmittedBytes`, the number of `redactions`, `metrics` and safe `recovery` links. A `DiagnosticMetric` is `Available` with a value or `Unavailable` with a reason and no value; an unavailable measurement is never a zero. `DiagnosticPage` carries the `latestSequence` a live tail continues from.
- **Logs.** `workspace.logs` filters by minimum `severity`, `outcome`, `operation`, `operationId`, `correlationId`, `targetId`, `stage` and `projectId`, a `search` of at most 256 characters and a `sinceMs`/`untilMs` window, newest first with `order: Descending`.
- **Reports.** `workspace.record_diagnostic` takes the run members above. The host attributes actor, correlation, project and origin; a reporter may not use a host-reserved component. A component is dot-separated lowercase segments (`a-z`, `0-9`, `_`, `-`), validated at admission and by the store and always matched exactly, so no spelling in another case passes for a host channel. Every nested text (metric names, units and reasons, recovery labels) passes the same redaction as the message, and counts toward `redactions`.

**Decision · confidence medium-high:** new record names with `x-earlier` instead of new members on `Diagnostic`, because 26 operations of other families carry `Diagnostic`, and each would otherwise have had to register a revision 2 it has no use for. `x-earlier` may name a generic schemars family (`Page`): the definition then merges into the family member it equals once the other renames apply, since the member's number (`Page19`) depends on which documents use it. **Decision · confidence medium-high:** an error class of its own (`DiagnosticErrorClass`) rather than the fault vocabulary, because a diagnostic classifies an observed cause (timeout, dependency, permission, corruption) that has no command fault. **Decision · confidence medium:** retained diagnostics default to 30 days and 50 000 records (`diagnostics.logRetentionDays`, `diagnostics.logMaxRecords`): a month covers recurring failures and post-incident review, and with 8 KiB messages and 16 KiB output the worst case stays near 1.2 GiB.

**Router availability revision 2 (3 November 2026).** `router.availability` registers revisions 1 and 2. The revision-1 input and result are unchanged; a revision-2 result projected onto revision 1 is the revision-1 result. Revision 2 adds an optional `sessionId` (a session the caller may see; another project's session is `NotFound`) and, on the result, that session's current `pin` (`RouteChoice`), `pinEligible` (whether it serves the asked intent, effort and capabilities right now) and `pinReason` (`Initial`, `Failover`, `SelectionChanged`, `EffortChanged` or `ConnectionChanged`). `RouteChoice` itself, which `router.route` and `router.pin` return, is unchanged.

**Decision · confidence medium-high:** the session's pin is reported by the availability query rather than by a new operation or new `RouteChoice` members, because the composer needs exactly that pair (what the conversation is pinned to, and whether its selection can be served now) in one bounded read, and no other recorded query returns a pin. **Decision · confidence medium:** a named-model intent never fails over to another model; when the named model is not eligible the route waits (`CapacityWait` with the earliest cooldown as `retryAtMs`) or is refused, because a named selection requests that model directly and any replacement pool would translate it to a tier. **Decision · confidence medium:** an explicit effort is routed only to a model that declares exactly that effort (no nearest-level mapping as in the reference router), so the requested and effective effort of a pin are always equal unless the request was `Default`.

**Owned browser sessions (DW-047, 3 November 2026).** The `browser.*` operations run on owned Chromium-family browsers through a native Rust Chrome DevTools Protocol client; no Node, Python or driver service is involved. A session is an owned resource of the principal that created it (`browser.sessions` Create): the host creates an empty owned profile directory under the data root, launches the browser through the process owner (shell/process preflight, durable launch record, owned process tree, bounded cancellation, boot recovery) and connects to its DevTools endpoint. Close stops the tree through the process owner and removes the profile only once the tree is verified gone; an unverifiable stop leaves the session `Uncertain` with its profile kept. Every session has its own profile, so concurrent sessions share no cookies, storage or cache. Boot recovery settles earlier boots' sessions from what process recovery verified (`Failed`, or `Closed` for one that was stopping) and removes profile roots no unsettled session owns; shutdown closes every session before the remaining owned trees are stopped. Revision 1 schemas are unchanged.
- **States.** The durable lifecycle is `Starting → Ready → Stopping → Closed`, with `Failed` (launch failure, browser exit, lost connection) and `Uncertain`. On the wire `BrowserSession.state` is `Partial` while starting, `Healthy` when ready, `Disabled` while stopping and once closed, `Failed` and `Unavailable` (uncertain). `processOwnerId` is the owned process tree once launched, the journaled Create operation before that.
- **Commands and completion.** Create, Close, navigation, input and upload commit an operation and a delivery to the `browser_effects` consumer and answer `Accepted`; the effect runs after commit with `Dispatching` committed first, and the typed result (`BrowserSessions`, `BrowserSnapshot`, `BrowserObservation`) is read as the operation's `OperationCompletion` (`BrowserService::completion`). Actions of one session run in commit order: each names the session's previous action and runs once it settled; deliveries are not partitioned, so a failed or held action never blocks later ones. An action waiting for its predecessor keeps its claim but holds no dispatcher worker, so waiting actions never delay Close or any other delivery. A replayed request key returns its receipt and never redispatches.
- **Revisions and references.** The session revision (`RevisionDimension::Connection`) advances on lifecycle changes and on every change of its registered targets (a popup, a target opened by navigation without `targetId`, a closed or crashed target); admitting an action does not change it. Targets are host IDs `t1`, `t2`, ...; a target's main frame is `<target>-f0` and other same-process frames `<target>-f<n>`. Every main-frame navigation, document replacement, frame change and renderer crash advances the target's document revision. Node IDs exist only in an accessibility snapshot (`n1`, `n2`, ... naming exact backend DOM nodes) and resolve only while the target's document revision equals the snapshot's and the snapshot is one of the target's last eight. A stale frame, document, snapshot or node is refused with `SourceChanged` (`RefreshAndNewRequest`) at admission and again at execution, where nothing is sent; nothing is ever re-resolved by role, name or selector. Input acts in the frame it names: a click is placed through every out-of-process frame owner; a scroll is sent at a point of the frame's visible part that hit-testing confirms reaches that frame (a frame out of view, clipped or covered is refused with nothing sent); a key is sent only while keyboard focus is in the named frame (its accessibility root is focused), otherwise it is refused (`browser_focus`).
- **Unknown outcomes.** A request sent without a response (timeout, lost connection, a session closed mid-action) is `OutcomeUnknown`, held for reconciliation and never re-executed. While a session has one, new navigation, input and upload are refused with `OutcomeUnknown` (`ReconcileOperation`) naming it, and an action admitted earlier fails without sending anything. Only a person states what it did (`BrowserService::resolve_unknown`, recorded as theirs); the held delivery is then settled by `queue.reconcile`.
- **File grants.** `browser.upload` and an `Artifact` page location accept only exact artifact versions the invocation may see now (digest, length and media type must match the version). Command preparation copies them, create-new and no-follow, into a fresh batch directory of the session's own root under safe single-component names of at most 128 UTF-8 bytes (`<n>-<name>`, a longer name cut on a character boundary keeping a short extension); a raw path is never accepted, an unrecorded batch is removed, and execution re-checks that the node is still exactly a file input (and accepts several files only with `multiple`).
- **Page policy.** Downloads are denied (`Browser.setDownloadBehavior`), the W3C permissions geolocation, notifications, MIDI, camera, microphone, clipboard, background sync, persistent storage, idle detection, display capture and window management are denied per session and every denial the browser refused is recorded with the session's `BrowserSessionReady` history, `alert` and `beforeunload` dialogs are accepted and `confirm`/`prompt` dismissed at once, popups are registered under the session, and out-of-process (cross-site) frames attach as flattened child sessions (`Target.setAutoAttach` with `flatten`): they are listed in the snapshot's frames (`outOfProcess`), inspected on their own session, driven like same-process frames (DOM reads on the frame's session, pointer input placed through the owner element's content box; a rotated or skewed frame owner is not supported) and advance the target's document revision. No page script, network interception, header, cookie or body is used or captured.
- **Evidence.** Accessibility snapshots, screenshots (PNG, full pages clipped at 16 384 CSS pixels), console and network notification batches and action observations are explicitly retained artifacts of the session's scope, linked to the creating work root and assignment and attributed to the session's principal and agent session. Texts are bounded (2 KiB per value, 5 000 nodes per snapshot, 256 KiB per notification batch, 2 000 buffered notifications per channel with drops reported as `truncated`) and redacted; URLs lose user info, fragments and credential-shaped query values. Typed input text is not repeated into evidence. An observation reports what the action observably did; delivering input is not a passed workflow.
- **Assets and qualification.** Each OS/CPU target reports its browser assets (`chrome`, `chromium`, `edge`, and `configured` for the `DEVWORKS_BROWSER` executable) as `workspace.diagnostics` health checks `browser.asset.<id>`: `Healthy` once a launch handshake verified it in this boot (product and DevTools protocol 1.3), `Degraded` when present but not yet verified, `Failed` after a failed handshake, `Unavailable` when missing or unsupported (Chrome and Edge publish no Linux arm64 build), and `browser.automation` `Unavailable` when no browser is present. Create with a missing or unqualified asset is refused (`UnsupportedCapability`, or `UnsupportedTarget` for an unknown ID); no session is started.
- **Authority.** Code reviewers are refused every browser operation (browser reads are not verified reads, and reviewers never mutate). A session is visible within its project, or for a workspace session to its owner, the user and the host; only its owner, the user or the host may drive or close it, and another project's principal does not learn it exists. A queued action whose owner's binding was revoked meanwhile is not performed. An archived project starts no session (`Conflict`, `archived_project`, also when it is archived before the launch); a deleted one is `NotFound`. The desktop Browser view lists the workspace's sessions with the selected project's, or every listed project's when none is selected, so a person can interrupt any session they may see.

**Decision · confidence medium-high:** browser commands answer `Accepted` with typed completions rather than `Applied`, because the effect is external and must run after the receipt commits with `Dispatching` journaled first; running it in command preparation would repeat it on a replay. **Decision · confidence medium:** ordering through a recorded predecessor instead of an ordered delivery partition, because a failed partition head blocks every later delivery until an operator acknowledges it. **Decision · confidence medium:** browser sessions take no capacity lease: they are headless owned process trees with their own profiles that contend for no shared physical resource, and a fixed browser capacity would act as the global cap UIQA-04 rules out; shared desktop focus, mouse and keyboard stay with desktop computer control's reservation. **Decision · confidence medium-high:** the DevTools transport is Chromium's private pipe (`--remote-debugging-pipe`, NUL-terminated JSON), never a port: the process owner launches the browser with a control channel of anonymous pipes (file descriptors 3 and 4 on macOS and Linux; on Windows two inherited handles named by `--remote-debugging-io-pipes=<in>,<out>`, the form Chromium's `AdoptPipes` reads), and only DevWorks holds the other ends, so no other local process can attach. The browser is ready once its first request (`Browser.getVersion`) is answered within the launch bound. **Decision · confidence medium:** a session's lifecycle, its observation index and its last admitted action are durable (migration 16); target, frame, document and snapshot state is not, because it dies with the browser process.

## Queries, cursors and event delivery

The initial typed read messages cover root state, advisory eligibility, operation status, receipt lookup and root-scoped history pages. Queries do not mint resume grants, clear blockers, claim work, consume a budget reservation or advance a required consumer checkpoint. Read caching may update disposable cache metadata under its own owner; it does not make the query a mutation of domain state.

A success response carries `ReadStamp`: store ID, restore epoch, committed watermark, scope revision and policy revision for that bounded snapshot. Recheck access before materialization/publication. The stamp is freshness/provenance, not a reusable authorization token or a claim of present eligibility. `BeginDispatch` rechecks all predicates atomically. Query failures are typed, including denied/not-found, `CursorExpired`, unavailable view/schema/store; no partial unauthorized content is returned with an error.

Cursors bind contract/query/filter digest, principal visibility, scope revision, store/restore epoch, keyset position and pinned view where applicable. A changed predicate/access/restore epoch or unavailable pin invalidates the cursor visibly. Mutable lists have per-page consistency; immutable snapshot queries retain their explicit pin. History pages follow committed sequence order, not time or UUID order; gaps caused by other roots or visibility filters are normal, not proof of lost delivery. Required consumer checkpoints follow their eligible delivery partitions rather than demanding adjacent global event numbers. For each page, `hasMore` refers to the response watermark. Return a continuation checkpoint even at the current tail so clients can poll without replaying the whole history. If retention removes the requested range, return `CursorExpired` with the correct resnapshot path rather than pretending an empty page is complete.

Persisted events are facts with stable event ID, global store sequence, aggregate identity/revision, actor attribution, causal command reference where applicable, optional validated project/root context, occurrence time and a typed versioned body. The candidate set includes command decisions, root-control changes, activation requests, blocker changes and operation observations. Event scope/context is host-owned; payload assertions cannot override stored target relationships. Aggregate revision may repeat for multiple facts in one transaction; event sequence is the ordering authority. The envelope identifies the aggregate revision dimension explicitly; root-control, work, blocker and operation counters are not interchangeable. A stale-owner observation is explicitly evidence-only and cannot authorize a current transition.

Durable handlers use stable consumer/event identity, fenced claims and the shared operation journal. State change, event and required delivery intent are atomic; handler changes/completion/follow-up intent are atomic. No event payload or cursor grants dispatch authority. At-least-once delivery remains explicit. Retryable delivery failure does not skip a required event or move the contiguous watermark over it. Other independent partitions continue. Unknown schema/upcaster failure holds the affected delivery with diagnostics; do not discard fields and acknowledge it. An optional UI projection may resnapshot current state after a gap, but that does not acknowledge required business work.

Live `watch`/`broadcast` messages only say state may have changed and carry a cursor/revision hint. Missing notifications and broadcast lag repair by durable query. A UI resubscription, package replay or broker reconnect does not resurrect feature/issue work. Per-session provider continuation serialization, preserved tool-call ordinals and later approval as a new event remain unchanged.
