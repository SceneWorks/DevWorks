Architecture feasibility review

2 November 2026 · Architecture baseline 1.0 · AD72–75

This records the original baseline 1.0 review. The current baseline is 1.1 following the user-requested MCP server amendment, owned by AD76–78 and DW-063/064. Its protocol/authentication/client integration remains implementation acceptance; none of the native experiments below tests the new server.

The original architectural design review is complete. The review resolves the four remaining design questions through native experiments, source/API inspection and explicit user decisions. Implementation has not started. Production correctness, recovery, retained capability parity, performance, accessibility and installer acceptance remain assigned to the local implementation plan.

Confidence is high in document consistency, the observed local experiments and the recorded decisions. Confidence is medium in eventual platform/provider integration until the actual adapters pass acceptance. Neither freezing this baseline nor accepting a provider risk demonstrates authenticated compatibility, security enforcement or cross-platform support.

Review scope and success criteria

The review covers requirements and interview decisions; the architecture and 43 diagrams; shared, provider/package, data/delivery and complete domain contracts; storage/queue comparisons; the capability/source inventory, acceptance/workload registers; native experiment records; the implementation plan; and the current UI prototype and its generated document editions. Historical evidence retains its original dates, pins, counts and limitations. Generated mirrors are checked against their authoring sources rather than treated as independent decisions.

Success requires consistent ownership and authority boundaries, a concrete native implementation route for required primitives, no unacknowledged product decision, complete operation/requirement/retained-source ownership, and an explicit separation between design closure and implementation acceptance. It does not require building production services to finish a design document. A failed production test cannot be waived by the baseline.

Security and native process design

Keep native credential values behind SecretStore: macOS Keychain; Windows user-scoped DPAPI; Linux Secret Service. App records hold references and revisions. Unavailable or locked facilities affect dependent actions; explicit session-only credentials are allowed and silent plaintext fallback is not. Native libraries/OS facilities do not introduce a DevWorks server. The DPAPI documentation describes user-scoped protection; the Secret Service specification describes session services and locked collections. Neither isolates secrets from all equivalent-user native code.

Process ownership and confinement are separate. Adopt saved launch identity/generation, minimal inherited handles/environment, actual exit observations and uncertain-resource retention. Windows uses non-breakaway Job Objects attached before execution; Unix uses groups plus child/identity tracking. Windows Job Objects support grouped lifecycle management but have documented breakaway/nesting conditions. The local cooperative group probe does not establish arbitrary descendant containment.

Full access remains the default policy with its documented ambient authority. Reviewers use verified brokered reads; arbitrary read-labeled executables do not become trusted reads. Restricted native profiles require the requested filesystem/network/IPC/credential guarantees. Linux Landlock plus complementary restrictions, Windows AppContainer and correctly signed macOS helpers remain implementation candidates. Landlock has ABI-dependent rights and inheritance; production admission must check the complete required profile. An unsupported profile returns unavailable and cannot fall back to Full. A partial sandbox is not a successful security qualification. No new privilege, mandatory VM or daemon is adopted.

Claude subscription and Anthropic API

The user chose the direct simple-router method after reviewing the possible claude -p alternative. No external Claude harness is adopted. The inspected reference is a556b3531b577173195bbc3876b556196447721d: ClaudeOAuthClient, ClaudeTokenProvider, ClaudeUpstream, ClaudeIdentity and the credential/options classes. It implements PKCE authorization/code exchange, stored token rotation and direct subscription bearer requests to Messages, with subscription beta and Claude Code identity transformation. These are source observations, not a live subscription result or an assertion of provider approval.

Anthropic's published authentication restriction excludes third-party Claude.ai subscription sign-in. The user elected to retain it at their risk. Settings must identify it as unsupported and optional, show the risk of lost access/account restriction and provide a separate API choice. Subscription starts disabled. Enabling requires current authenticated human acceptance, bound to the exact notice digest and connection/account/profile revision. A boolean in agent JSON, imported setting or package declaration cannot grant that acceptance. Revoke it on notice/account/profile change, explicit withdrawal or restore. Ordinary same-account refresh retains the decision. This is a product risk decision; it does not alter Anthropic's position.

AnthropicMessages uses a separate API-key connection and documented API authentication, with a version-qualified Messages profile. Do not copy subscription identity/beta behavior into that profile. Both go through the same native router, broker and attribution services. Distinct secrets, native continuation bindings, model/capability snapshots, cooldowns and billing classifications remain mandatory. API billing is not subscription usage. Report actual charges where available and otherwise dated estimates; subscription uses the confirmed API-equivalent budget estimate. Explicit routing may include both connections; failover cannot silently introduce API billing outside that configured set.

The operation catalog already has separate endpoint variants. The revised router.configure candidate adds exact-notice acceptance/revocation intent under host-authenticated human configuration. A connection response exposes host-derived acceptance and notice digest. No catalog operation is added. The public SDK remains a candidate until full host/SDK interoperability; it never owns the user's risk decision, credentials or authority.

OpenAI also documents a native ChatGPT-plan OAuth path for eligible open-source/local apps. Its sign-in and preview requirements are distinct from the frozen simple-router Codex device/backend profile. Record them as a source-supported native alternative, not a silently substituted requirement or proven account entitlement. DW-018/019 must qualify the selected profile and preserve the confirmed connection lifecycle.

Native UI integration

Adopt the matching eframe window integration with explicit native AccessKit support; the probe uses Glow as one concrete renderer. Other renderers remain adapter choices subject to target evidence. eframe's features expose native rendering and AccessKit; egui accessibility guidance describes labels and custom-widget semantics. The version lock and native binary are recorded in the evidence manifest.

Widget IDs, roles, names, label relationships, focus order and keyboard actions belong to the view contract. Custom boards, graph/schema viewers, diffs and virtualized transcript blocks require meaningful semantic nodes and keyboard equivalents. Preserve focused/selected items across projection updates, avoid duplicate live announcements and do not announce each streamed token. Native file/dialog/clipboard adapters resolve host-authorized handles. Presentation state remains UI-owned; sessions, drafts, attachments and pins remain service-owned. Two invisible frames prove initialization only; all retained interactions and OS assistive technology remain acceptance obligations.

Baseline and change control

Baseline 1.0 adopts component/dependency direction, authority, durable effects/recovery, persistence, routing/session/package boundaries and capability scope. It preserves 345 requirements (208 Confirmed, 137 Proposed), all 347 operations/47 families, 494 retained frozen source entries, 64 audited exclusions, 33 acceptance groups and 12 unexecuted production workloads. The plan has 61 active slices, with DW-038 retired without renumbering other IDs. Proposed requirement status and the candidate public protocol remain explicit.

Correctness/recovery, full retained behavior, actual service/SDK/transport integration, cross-platform security/accessibility, performance and installer checks are implementation acceptance under G01–G12. Each capability must pass its affected admission gate before being advertised. A material contradiction requiring changed authority, retained scope, recovery semantics or a mandatory runtime reopens architecture with concrete evidence. Routine adapter fixes and test failures stay in their owning slices. Planning remains local; no Shortcut records, application implementation or real inference were created by this review.
