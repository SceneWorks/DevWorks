# DevWorks agent notes

## Feature Plan Review

Before implementation, run one independent review of a substantive feature plan, such as a plan that changes a shared contract, coordinates several repositories, or changes durable state or recovery behavior.

- Start a fresh, read-only reviewer session without the planning conversation or its summaries. Give it the exact plan revision and its acceptance criteria. Ask it to identify material ambiguities, missing acceptance cases, and assumptions a fresh implementer would have to guess. Start with the plan alone, then provide relevant source at a named revision if the reviewer needs to check its fit with the code. Zero findings is a valid result.
- The coordinator checks the findings against the requirements, CodeGraph items, and current source. Record the reviewed revision and the disposition of each material finding in CodeGraph. Update the plan and affected acceptance criteria as needed. Use the existing readiness and approval rules for closure and escalation.
- Reuse current evidence on Continue. If a material change invalidates it, review the affected scope. If the harness cannot start an isolated reviewer, record that the review was unavailable and surface it in the readiness assessment.

## Pull requests

- **Feature work.** Each CodeGraph feature gets one pushed branch, `feature/<feature-key>` (for example `feature/dw-f16`). Each item of the feature is built on its own local branch and worktree, gets exactly one independent review, has its valid findings fixed, and is merged locally into the feature branch, which is then pushed. Items do not get their own PRs, and nobody waits for CI between items.
- **Feature PRs.** When every item of a feature is integrated and the feature's acceptance passes, open one PR per repository from the feature branch to `main`, naming every item it carries. It needs passing CI. Automated review runs for at most 5 rounds, and every valid finding is fixed within them. After the fifth, request no more reviews: fix only blocker and major findings, file every other remaining finding as a CodeGraph bug, link it in the thread reply, and merge on passing CI.
- **Other work** (a standalone item outside a feature, a hotfix): group related CodeGraph items into one PR. Items are related when a reviewer would read them together: the same subsystem or files, the same kind of change, or follow-ups to the same feature. Keep unrelated items in separate PRs, and name every item in the PR body. Automated review runs for at most 3 rounds; after the third, file each remaining finding as a CodeGraph bug, link it in the thread reply, and merge on passing CI.
- Do not merge one open PR's branch into another; if work depends on an unmerged PR, add it to that PR's branch while it is open, wait for it to merge, or put both on a feature branch.
- Keep each non-feature PR at or under 5000 hand-written changed lines. The `PR size` workflow enforces this (`tools/pr-size/check.py`); files marked `linguist-generated` in `.gitattributes` are not counted, and PRs from `feature/*` branches are not checked.
- Every item still needs its own tests and acceptance report. Land incomplete capabilities unwired (not reachable from the UI or agent tools) rather than holding a long-lived draft PR.

## Code Review Rules

Apply these rules to automated and human PR reviews.

- Report only defects introduced by the PR's hand-written changes. Skip files marked `linguist-generated` in `.gitattributes`, including generated contracts, fixtures, Rust, and lockfiles. Review the inputs and generators that produce them, including `tools/contracts-eval/domain-spec.json` and `docs/architecture/contracts/family-coverage.json` where applicable.
- Trace changed behavior from its normal entry points, such as the desktop UI, agent tools, MCP, or scheduled jobs, through affected callers and operation contracts. Check compatibility with existing inputs, saved data, and supported contract revisions. Follow failure, cancellation, and retry paths through any state changes. If an important regression lacks coverage, name the specific case a test should exercise.
- Look for an existing shared implementation before accepting a new path. Flag copied logic, parallel implementations, and fixes limited to one caller when the shared implementation can handle the behavior. Cite the shared path and name the behavior that could diverge.
- For model and provider changes, check that requests use the shared inference router for validation, model selection, admission, retries, and usage accounting where applicable. Check that cancellation and failures propagate to the job or session that owns the request. Keep provider-specific authentication, wire formats, streaming, and error translation behind existing adapter interfaces. Reuse existing download and loading paths if the change manages local models. Prefer extending the shared path when it lacks required behavior. A separate path needs a concrete model or provider constraint and should keep common behavior in shared code.
- Respect the boundary between core services, ports, and adapters. Keep one owner for each piece of shared state and check that changes go through that owner's operations and transactions. Flag obsolete branches or fallbacks left by the change when they can route callers through stale behavior or obscure the active path.
- Trace affected trust boundaries, including MCP and extension requests, tool calls through the broker, and file and network access. Flag missing authorization, unchecked paths or URLs, secrets in logs or persisted diagnostics, and invalid inputs that bypass shared validation.
- Check the cost of changed hot paths. Flag repeated database queries, graph traversal, file reads or hashing, provider requests or downloads, blocking I/O on async executor threads, large buffer copies, and unbounded concurrency when they have a concrete impact.
- Anchor each finding to a changed line. Explain the concrete failure or maintenance risk, suggest the smallest practical fix, and match severity to the impact. State what would verify any material uncertainty.

## Host storage (dev-host)

- **Root and variable.** All machine-local disposable state lives under one root named by `DEV_HOST_ROOT`, on dedicated storage with a `.dev-host-root` marker. Never hardcode a machine path for that state; derive it from `DEV_HOST_ROOT`.
- **Layout under the root** (dev-host 0.2.0; one root may be shared by several hosts): shared `weights/<project>` (with its manifest), `cache/<project>` (entries written whole and renamed into place) and `campaigns/<project>/<id>/evidence`; everything else in this host's own folder `hosts/<host>/` (`<host>` as the OS reports it): `locks/`, `cache/<project>` (caches updated in place), `build/<project>/<key>/slot-<n>` (cargo build slots), `t/<8-char id>` (temp folders), `campaigns/<project>/<id>/work`, `runner/<name>`, `docker/`. `dev-host init-host` creates `hosts/<host>/` once; `dev-host lock-dir` prints its `locks/`.
- **The tool.** `dev-host` lives in this repo at `crates/dev-host` and builds with plain `cargo build -p dev-host`. Install a released version with `dev-host install --version X` (macOS arm64 and Windows x64). `dev-host check` verifies the root; `eval "$(dev-host env --format sh)"` points `CARGO_TARGET_DIR` at a build slot and `TMPDIR` at the root. The Claude Code SessionStart hook (`.claude/hooks/dev-host-env.sh`) runs `dev-host env` for every session; without dev-host or `DEV_HOST_ROOT` it prints one warning and the session keeps the defaults. Find build output with `cargo metadata --format-version 1 --no-deps` (`.target_directory`), never by assuming `<repo>/target`.
- **Guard.** CI runs `dev-host guard --diff <base>` on every PR. Run `dev-host guard --all` and `dev-host guard --docs` locally. Mark a deliberate path (a path inside a container, a rejection fixture, a citation) with `dev-host: allow-path <reason>` on the same line, and make the reason true.
- **Searching.** Never search from `/` or `$HOME` (no `find /`, `find ~` or `find $HOME`): it walks synced and network folders. Name the folders to search.
